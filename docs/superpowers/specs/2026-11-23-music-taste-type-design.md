- 상태: 승인 (2026-11-24, 상현)

## 1. 무엇을 왜 만드나

지금 추천은 모든 사용자에게 같은 흐름을 쓴다(음악 치료의 동질 원리). 그런데 같은 "가라앉음"이라도 밝은 곡으로 위로받고 싶은 사람이 있고, 끝까지 잔잔한 곡에 머물고 싶은 사람이 있다.

이 기능은 기존 흐름(기록 → 감정 짐작 → 사용자 확인 → 3곡 추천 → 판 저장)을 그대로 두고, 추천 직전에 "이 사람은 그 감정일 때 어떤 노래를 원하는가"를 한 번 더 반영한다.

- 감정 분석: 지금 어떤 기분인가
- 유형 검사: 그 기분일 때 어떤 노래를 원하는가

발표에서 근거 질문에 답할 수 있도록, 축은 음악 기분 조절 연구(사리칼리오의 7가지 방식)에서 가져온다.

## 2. 목표 · 목표 아님 · 실패로 보는 것

**목표**
- 유형 검사 결과가 실제 추천 3곡을 바꾼다.
- 12문항, 1분 안에 끝난다.

- 시연 기기 한 대를 돌려 쓰는 평가에서 참여자마다 기록·유형이 섞이지 않는다 (12절).

**목표 아님**
- 좋아요·건너뛰기로 유형을 자동 조정하기

- 슬픔·분노를 자세히 캐묻는 문항

**실패로 보는 것**
- 검사 결과가 추천에 영향을 주지 않는 이름뿐인 기능
- 검사를 건너뛸 수 없거나, 첫 기록 전에 검사를 강요하는 것 (11/18 결정 "처음 들어가면 바로 쓰기" 위반)

## 5. 4개 축

감정 4종마다 축 1개, 축마다 두 쪽. 앞쪽이 지금 방식(기본값)이다.

| 축 | 감정 | 기본 쪽 (지금 방식) | 다른 쪽 | 연구 근거 |
|---|---|---|---|---|
| 1 | 가라앉음 | `위로`: 맞추기 → 점점 밝게 | `머무름`: 끝까지 잔잔하고 어두운 곡 | 위로받기 |
| 2 | 예민함 | `진정`: 점점 에너지 낮추기 | `발산`: 강하고 센 곡으로 쏟아내기 | 감정 쏟아내기 |
| 3 | 좋음 | `유지`: 비슷한 밝은 곡 | `증폭`: 더 신나는 곡으로 끌어올리기 | 즐기기 |
| 4 | 무난함 | `잔잔`: 비슷한 보통 곡 | `전환`: 밝고 활기찬 곡으로 기분 바꾸기 | 기운 되찾기 |

### 6.3 문항 (한 화면에 한 문항, 진행 표시 `3 / 12`)

축마다 3문항. "가"는 기본 쪽, "나"는 다른 쪽. 축마다 많이 고른 쪽으로 정한다 (3문항이라 동점 없음). 문항 순서는 축을 섞어서 1→2→3→4→1… 순으로 보여 준다.

**축 1 · 가라앉음 (위로 / 머무름)**
1. 마음이 가라앉은 날, 이어폰을 꽂으면? — 가. 처음엔 차분하다가 점점 밝아지는 노래 / 나. 지금 기분 그대로인 잔잔한 노래
2. 슬픈 영화를 보고 난 뒤라면? — 가. 기분을 풀어 줄 노래를 찾는다 / 나. 여운에 맞는 노래를 더 듣는다
3. 친구가 우울하다고 할 때 노래를 골라 준다면? — 가. 힘이 나는 노래 / 나. 마음을 알아주는 노래

**축 2 · 예민함 (진정 / 발산)**
4. 신경이 곤두선 날 듣고 싶은 노래는? — 가. 숨이 고르게 쉬어지는 차분한 노래 / 나. 속이 시원해지는 세고 빠른 노래
5. 시험이나 마감 직전 머리가 복잡할 때는? — 가. 소리를 줄이고 조용한 곡을 튼다 / 나. 볼륨을 올리고 강한 곡을 튼다
6. 화가 난 친구에게 노래를 골라 준다면? — 가. 마음을 가라앉혀 줄 노래 / 나. 대신 소리쳐 주는 듯한 노래

**축 3 · 좋음 (유지 / 증폭)**
7. 기분 좋은 날, 이어폰을 꽂으면? — 가. 지금 기분처럼 편안하고 밝은 노래 / 나. 더 신나서 몸이 들썩이는 노래
8. 좋은 소식을 들은 직후라면? — 가. 좋은 기분을 천천히 즐길 노래 / 나. 기분을 더 끌어올릴 노래
9. 신난 친구와 같이 들을 노래를 고른다면? — 가. 둘이 흥얼거릴 밝은 노래 / 나. 같이 뛰어오를 만큼 신나는 노래

**축 4 · 무난함 (잔잔 / 전환)**
10. 별일 없는 평범한 날, 이어폰을 꽂으면? — 가. 배경처럼 편하게 흐르는 노래 / 나. 하루에 활기를 더해 줄 노래
11. 출근·등굣길이 그저 그런 기분일 때는? — 가. 지금 분위기에 맞는 무난한 노래 / 나. 기분을 바꿔 줄 밝은 노래
12. 심심하다는 친구에게 노래를 골라 준다면? — 가. 편하게 들을 만한 노래 / 나. 기분 전환이 될 신나는 노래

## 7. 저장 · API

### 7.1 브라우저 (`localStorage`)

| 키 | 값 |
|---|---|
| `moodwave.mvp.taste.v1` | `{"sides":{"가라앉음":"위로","예민함":"발산","좋음":"유지","무난함":"전환"},"answers":["가","나",…12개],"takenAt":"2026-11-30T10:00:00+09:00"}` |
| `moodwave.mvp.taste.offered.v1` | `true` (권유를 한 번 보여 줬음) |

읽기·쓰기는 기존 `read()`/`write()` 헬퍼(try/catch 포함)를 쓴다.

- `answers[i]`는 **문항 번호 i+1의 답**이다 (보여 준 순서가 아님).
- 읽을 때 `sides`의 감정마다 그 감정의 두 쪽 중 하나인지 확인한다. 깨졌거나 맞지 않는 감정은 기본 쪽으로 보고 `taste_side`를 보내지 않는다. 그래야 잘못 저장된 값 때문에 추천 요청이 422로 막히지 않는다.

### 7.2 `POST /api/recommendations`

요청에 선택 항목 하나를 더한다.

```json
{"record_id": 12, "confirmed_emotion": "가라앉음", "taste_side": "머무름"}
```

- `taste_side`가 없거나 `null`이면 기본 쪽으로 계산하고, DB에는 `NULL`로 저장한다 (검사 안 함과 기본 쪽 선택을 구분하기 위해).
- 값은 `confirmed_emotion`의 두 쪽 중 하나여야 한다. 아니면 **422** (예: 가라앉음 + 발산).
- 화면은 `sides[confirmed_emotion]`을 보낸다.
- 응답 양식은 그대로 (`songs[].step`에 새 단계 이름이 들어감).

### 7.3 DB

`tb_record`에 열 하나 추가:

```sql
taste_side TEXT CHECK (taste_side IN ('위로','머무름','진정','발산','유지','증폭','잔잔','전환'))  -- 추천에 쓴 쪽, 검사 안 했으면 NULL
```

- `schema.sql`의 `CREATE TABLE`에 넣는다 (새 DB).
- 이미 있는 DB: `init_db()`에서 `PRAGMA table_info(tb_record)`로 열이 없으면 `ALTER TABLE tb_record ADD COLUMN …`을 실행한다.
- 추천할 때 `emotion_final`과 함께 `taste_side`도 갱신한다.
- 같은 날 다시 기록할 때(`db.save_today_record`의 덮어쓰기)는 `emotion_final`처럼 `taste_side = NULL`로 비운다. 비우지 않으면 추천 전에 나간 기록에 이전 쪽이 남아 평가에 섞인다.
- "감정과 쪽의 짝"(가라앉음 + 발산 금지)은 API의 422로만 지킨다. SQLite의 `ALTER TABLE ADD COLUMN`은 다른 열을 보는 CHECK를 붙일 수 없기 때문이다.

## 8. 추천 계산 (`backend/app/recommender.py`)

`TARGETS`를 "감정 × 쪽" 8개 표로 나눈다. 기존 4개는 숫자 그대로 기본 쪽이 된다.

| 감정·쪽 | 1번 곡 | 2번 곡 | 3번 곡 | 순서 조건 |
|---|---|---|---|---|
| 가라앉음·위로 (기존) | 0.20, 0.30 맞추기 | 0.45, 0.32 조금 밝게 | 0.70, 0.35 더 밝게 | 다음 곡이 더 밝음 (기존) |
| 가라앉음·머무름 | 0.20, 0.30 맞추기 | 0.22, 0.25 곁에 머물기 | 0.28, 0.22 잔잔하게 마무리 | 없음 |
| 예민함·진정 (기존) | 0.25, 0.85 맞추기 | 0.30, 0.50 에너지 낮추기 | 0.55, 0.30 차분하고 조금 밝게 | 기존 그대로 |
| 예민함·발산 | 0.25, 0.85 맞추기 | 0.22, 0.88 쏟아내기 | 0.30, 0.80 끝까지 쏟아내기 | 없음 |
| 좋음·유지 (기존) | 0.80, 0.70 | 0.78, 0.72 | 0.82, 0.68 (비슷한 분위기 1~3) | 없음 |
| 좋음·증폭 | 0.80, 0.70 맞추기 | 0.83, 0.80 더 신나게 | 0.85, 0.88 끌어올리기 | 없음 |
| 무난함·잔잔 (기존) | 0.50, 0.40 | 0.55, 0.45 | 0.52, 0.42 (비슷한 분위기 1~3) | 없음 |
| 무난함·전환 | 0.50, 0.40 맞추기 | 0.65, 0.55 조금 밝게 | 0.78, 0.65 활기차게 | 없음 |

(숫자는 밝기 valence, 에너지 arousal. 새 표 4개는 초안이며 사용자 평가 뒤 조정한다.)

- `recommend_three(emotion, recent, *, side=None, candidates=None)`: `side`가 `None`이면 기본 쪽.
- `_can_follow`와 DP(가라앉음·예민함 전용 분기)는 **순서 조건이 있는 표(위로, 진정)에서만** 쓴다. 지금 `emotion in {"가라앉음","예민함"}`로 고른 부분을 "그 표에 순서 조건이 있는가"로 바꾼다.
- 순서 조건이 없는 새 표에는 #23의 "최근 추천곡 우선 제외" 때문에 분위기가 먼 곡이 뽑힐 수 있다 (#23 리뷰 1번). 9절의 곡 수 확인으로 판단하고, 부족하면 건호와 거리 상한을 함께 정한다.

## 9. 시작 전 확인: DEAM 구역별 곡 수

새 쪽 4개가 쓸 구역에 DEAM 곡이 **30곡 이상**인지 센다. 30곡 미만인 축은 구역 경계를 넓히거나 그 축만 PMEmo를 함께 쓰는 방안을 다시 논의한다.

| 새 쪽 | 구역 (0~1) |
|---|---|
| 머무름 | 밝기 < 0.4, 에너지 < 0.4 |
| 발산 | 밝기 < 0.4, 에너지 > 0.6 |
| 증폭 | 밝기 > 0.6, 에너지 > 0.7 |
| 전환 | 밝기 > 0.6, 에너지 > 0.5 |

세는 스크립트는 일회용이라 저장소에 넣지 않는다. 실제 점수표는 건호에게 받기로 했다 (11/23 요청).

## 10. 시험

**백엔드 (`backend/tests/`)**
- 8개 표 각각: 대표 후보로 3곡이 그 표의 단계 이름(`step`)으로 나온다
- 머무름·발산·증폭·전환에서 순서 조건 없이 3곡이 나온다
- `taste_side` 없음 → 기본 쪽 결과와 같고 DB `taste_side`는 `NULL`
- `taste_side`가 감정과 안 맞음 → 422
- `taste_side` 저장 확인
- 같은 날 다시 기록하면 `taste_side`가 `NULL`로 비워진다
- 열이 없는 옛 DB로 서버를 켜면 열이 추가된다

**프론트 (`frontend/tests/`, `node --test`)**
- 12개 답(문항 번호 순) → 축별 쪽 계산 (많이 고른 쪽)
- 깨진 `localStorage` 값 → 결과 없음
- 감정과 맞지 않는 쪽이 저장돼 있음 → 그 감정은 `taste_side`를 보내지 않음

- 참여자 코드: 헤더 없음 → 시연 사용자, 서로 다른 코드 → 서로 다른 `user_id`, 같은 날 두 참여자의 기록이 둘 다 남음, 형식이 틀린 코드 → 422
- 참여자 코드: 최근 7일 추천곡 제외가 그 참여자의 기록만 본다

**손 확인**
- 권유 → 건너뛰기 → 다음 추천에 권유 안 나옴
- 권유 → 검사 → 결과 → 추천 3곡의 `step`이 새 단계 이름
- 마이 → Day Type → 다시 검사 → 다음 추천에 반영
- 마이 → 다음 참여자로 시작 → 새 코드가 보이고, 일기·유형·권유 기록이 비어 있고, 다음 추천 전에 권유가 다시 나옴

## 11. 축별로 맞았는지 판단하기 (12/7 평가)

앱의 감상 후 기분 질문은 가라앉음·예민함 날에만 나오고, 머무름·발산은 기분을 나아지게 하려는 쪽이 아니라 그 질문으로는 판단할 수 없다. 그래서 **12/7 설문 문항 + 이미 저장되는 신호**로 판단한다. 앱에 새로 만드는 화면은 없다.

**설문 (참여자마다, 참여자 코드를 함께 적음)**
- "유형 결과가 평소 나와 맞나요?" (1~5)
- 그날 추천을 받은 감정에 대해: "추천 3곡이 그 기분일 때 듣고 싶던 방향이었나요?" (1~5)

**이미 저장되는 신호 (`tb_record_song`)**
- 좋아요(`is_liked`), 건너뛰기(`is_skipped`), 끝까지 들음(`is_completed`)
- 축마다 `taste_side`로 기록을 셋으로 나눠 곡당 비율을 비교한다: 다른 쪽 / 기본 쪽을 고름 / 검사 안 함(`NULL`)
- 다른 쪽을 고른 사람의 건너뛰기 비율이 기본 쪽 추천을 받던 때보다 낮고, 설문 점수가 3 이상이면 그 축은 "맞았다"고 본다

**한계 (발표에서 밝힘)**
- 쪽마다 사람 수가 몇 명뿐이라 통계 검정은 하지 않고 비율과 설문 평균만 보인다
- 쪽을 고른 사람과 안 고른 사람이 다르므로 비교는 참고용이다

조회는 일회용 SQL이라 저장소에 넣지 않는다.

## 12. 다음 참여자로 시작 (참여자 코드)

12/7 평가는 시연 기기 한 대를 돌려 쓴다. 화면(`localStorage`)과 서버(`tb_record`) 둘 다 참여자별로 나눠야 한다.

**화면**
- 마이 화면에 [다음 참여자로 시작] 버튼. 누르면 "지금 기록이 이 기기에서 지워져요" 확인을 받은 뒤 진행한다.
- `moodwave.mvp.`로 시작하는 키를 모두 지운다 (일기 기록, 유형, 권유했음 포함). 그리고 새 참여자 코드를 만들어 `moodwave.mvp.participant.v1`에 저장한다.
- 코드는 영문 대문자·숫자 4자리 (예: `K7QM`). 마이 화면에 크게 보여 줘서 참여자가 설문에 적게 한다.
- 모든 API 요청에 `X-Participant: K7QM` 헤더를 붙인다. `frontend/src/api.js`의 `request()` 한 곳에서 붙인다.
- 코드가 없으면(평소 사용) 헤더를 보내지 않는다.

**서버**
- 헤더가 없으면 지금처럼 시연 사용자(`get_demo_user_id`).
- 헤더가 있으면 그 코드의 `tb_user`를 찾고, 없으면 만든다 (`email = participant-K7QM@moodwave.local`). 새 테이블·열은 없다.
- 코드 형식(`^[A-Z0-9]{4}$`)이 틀리면 **422**. 헤더 값은 사용자가 바꿀 수 있는 입력이라 서버에서 확인한다.
- `get_demo_user_id(con)`를 부르는 곳(지금 `main.py` 두 곳)과, 기록 id로 조회하는 경로가 다른 참여자의 기록을 보지 않는지 함께 바꾼다.
- 서버·DB 쪽이라 건호에게 알리고 누가 만들지 정한다.
